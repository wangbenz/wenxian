# V0.15 灰度测试问题记录

> 记录时间：2026-08-13（北京时间）
>
> 当前状态：2026-08-15 的可信引用与事实投影增强已部署至 V0.15 隔离服务，完成 RDS 单回合与 H5 基础冒烟；尚未切换正式流量
>
> 记录目的：保留真实回放证据，避免把同一根因拆成多个临时补丁。

## 处理原则

V0.15 的可信剧情遵循同一条边界：

> 系统保护已经确认的事实，但不限制玩家创造尚未发生的可能。

- 已经写入命卷的经历、人物、关系和线索，后续不得被系统无故否认。
- 玩家可以尝试尚未发生的行动；行动是否成功以及产生什么后果，由本轮剧情决定。
- 只有与已确认事实真正冲突的输入才应被拦截，不能因为某个名字没有进入实体索引就直接判定其不存在。
- 本文只记录问题与证据，不修改玩家数据，也不确定最终技术方案。

**优先级：P0**

**影响范围：可信上下文、系统推荐选项、自由行动、人物连续性**

### 已确认的共同现象

1. 柳青儿、驿站伙计、路人和老周并不是玩家凭空修改的既有事实：它们来自角色根源、已提交剧情或系统自己提供的下一步选项。
2. 对应命卷的剧情正文、推荐选项或物品描述中可以找到这些人物和线索，但 `story_entity` 中没有相应人物实体。
3. 当前行动裁决主要依赖实体索引。对象没有进入实体索引时，会被标记为 `UNRESOLVED`，随后被 Java 校验器拒绝。
4. `WX-20260813-CCE009` 与 `WX-20260813-F07186` 是同一行动意图的两种表述。将“老周”写得更具体并不能解决事实来源缺失。
5. 失败操作没有推进命卷回合、修订号和世界时间，也没有覆盖已有状态；但前置裁决可能已经产生模型请求和等待成本。

### 玩家体验影响

- 系统先介绍人物或给出选项，下一轮又声称该人物不存在，直接破坏可信剧情承诺。
- 玩家无法判断推荐选项是否真的可执行，只能反复改写输入或退出重进。
- 自由行动被误判为“篡改事实”。例如攻击老周属于玩家可以尝试的行动，系统应裁定行动结果，而不是否认老周存在。
- 相同输入反复失败会放大延迟、模型消耗和客服排查成本。

### 当前根因判断

目前可信来源之间尚未形成完整引用链：

```text
角色根源 / 世界事实 / 已提交剧情 / 系统推荐选项
                    ↓ 引用未保留
              下一轮行动裁决
                    ↓
         只在实体索引中查找目标
                    ↓
        未找到即被当作“不存在”并拒绝
```

这不是单纯的“缺少几个 NPC 数据”，而是权威事实模型仍有断层：

- 推荐选项目前缺少稳定选项身份和事实引用；
- 行动请求无法证明它来自上一轮系统推荐选项；
- 普通剧情人物未必会被及时投影为人物实体；
- 裁决无法区分“没有进入实体索引”和“已确认不存在或相互冲突”。

### 后续统一设计时必须满足的验收条件

1. 同一修订号下，系统刚生成的推荐选项必须可以直接执行。
2. 已提交剧情中持续出现的人物，可以作为下一轮行动对象，不要求玩家重新解释其身份。
3. 角色根源和已确认世界事实中的人物、物品与线索，可以被后续行动可靠引用。
4. “未知但可以尝试”与“违反已确认事实”必须使用不同结论，前者不得被直接拒绝。
5. 不把所有正文名字都强制创建为永久人物，也不让人物关系和背包无限膨胀。
6. 不使用姓名关键词、正则白名单或针对单个问题编号的 Java 分支修复。
7. 不让“系统推荐选项”无条件绕过事实校验；选项本身也必须携带可追溯的事实依据。
8. 对攻击、赠送、交易、服用、闭关等自由行动，只保护前置事实和提交一致性，不替玩家预设成功或失败。

### 暂不执行的操作

- 不手工补写柳青儿、老周等人物数据。
- 不针对上述编号增加名称匹配规则。
- 不放宽所有 `UNRESOLVED` 输入直接通过。
- 不在本轮修改行动裁决、实体表结构或 Prompt。

后续应先完成“可信来源与引用协议”的统一方案，再用上述四个问题编号建立真实回放用例并一次性验证。

### 2026-08-14 统一实现进度

- 已把角色根源、开场、上一回合和当前系统推荐选项纳入可追溯来源目录；

## 全部受邀账号样本概况

本轮共核对 `v015-gray-01` 至 `v015-gray-10` 十个受邀测试账号：

- 6 个账号实际推进剧情，共成功提交 127 回合；
- 5 个账号产生服务端错误，共记录 75 次失败响应；
- 1 个账号创建命卷但没有推进；
- 3 个账号尚未创建命卷；
- 成功回合序号连续，世界时间没有倒退；
- 失败请求没有写入正式回合，但可能已经产生模型调用、等待和重复提交。

下列分类按共同根因整理，不等同于 HTTP 错误码分类。

## P0-A：角色创建结果没有形成统一的初始事实契约

角色名称、种族、境界、角色根源、游玩偏好和所选世界目前可能彼此矛盾，进入第一回合后也没有被统一投影为可引用事实。

真实样本包括：

- 角色根源写明柳青儿和毁灭之镯，后续裁决却认为两者不存在；
- 角色根源写明幼时得到醒尘剑，后续拿取或寻找醒尘剑被拒绝；
- 角色根源写明天机阁少宗主，剧情能描写其身份，后续行动却不能稳定引用天机阁相关经历；
- 角色根源要求“此世界没有修士，采用江湖体系”，所选官方世界仍是仙朝宗门世界；
- 角色根源设定为末法地球转生，开场却落在玄墟界青岐州的古代环境；
- 九尾天狐根源写明修炼如饮水且当世无敌，但结构化初始境界仍为启灵，之后连续多轮被普通瓶颈卡住；
- 许愿命格明确允许无代价实现愿望时，相似许愿有时成功、有时又被前置裁决拒绝。

这类问题同时破坏“已确认设定不会被遗忘”和不同玩家选择爽文、凡人、江湖或弱约束世界的自由。

## P0-B：已提交剧情与下一轮行动之间缺少可信引用链

当前长期实体索引偏向记录物品和地点，普通人物很少被登记。在本轮样本中，多份已推进 10 至 33 回合的命卷仍然没有任何人物实体。

结果是：

- 正文中已经持续出现的老周，下一轮无法作为攻击、交谈或追踪对象；
- 系统自己生成的“向驿站伙计打听”无法执行；
- 已经到达宗门接待处后，系统仍无法确认青云宗弟子；
- 正文刚出现的青衫男子，下一轮询问时被判为不存在。

问题不应通过“正文中所有名字都创建永久人物”解决。需要区分长期人物、当前场景人物、泛指角色和纯气氛描写，并让推荐选项携带可追溯引用。

## P0-C：把“玩家尝试”错误等同于“玩家声明事实”

行动裁决目前过早回答“对象是否已经存在”，但玩家输入可能只是寻找、询问、许愿、调查、攻击或尝试获得。

必须区分：

- “我已经拥有仙剑”是对既有事实的声明；
- “我去寻找仙剑”是尚未发生的尝试；
- “我许愿感知仙剑方位”是使用已确认能力发起尝试；
- “攻击老周”只授权攻击行为，不代表攻击必定成功或老周必定死亡；
- “向附近弟子打听”允许剧情生成一个符合现场的普通弟子，不要求该弟子预先成为永久人物。

当前系统对这些语义使用同一种 `UNRESOLVED` 处理，造成“拦的奇怪”；另一方面，真正结果也不能由玩家一句话直接写入，而必须经过剧情生成、审阅和事务提交。

## P0-D：行动契约、剧情补丁和 Reducer 使用的实体语义不一致

本轮共有 23 次 `STORY_PATCH_REJECTED`。已观察到的主要原因不是剧情不安全，而是结构协议内部不一致：

- 能力被错误附加物品保管关系；
- 新物品在行动契约中没有声明最终保管者；
- 物品“随身持有”与保管者字段互相矛盾；
- 已有实体缺少稳定 ID，或稳定 ID 与标准名称不一致；
- 同一对象在行动解析与剧情补丁中被识别成不同类型；
- 发生一次空主键导致的空指针异常。

当前“一次生成、一次修复、仍不合法就整轮失败”的方式保护了数据库，但把模型结构波动直接暴露成玩家无法推进，并产生额外延迟和 Token 消耗。

## P0-E：玩家决定保护的粒度不稳定

独立审阅能够识别 AI 替玩家做重大决定，这是正确方向；但当前行动契约的 `authorizedActions`、停止点和 `requiredEndState` 之间经常互相矛盾。

样本表现为：

- 玩家授权进入藏经阁并使用测灵碑，停止点却被解析成“到达外院后停止”；
- 查看锦囊后将锦囊放回、观察四周等轻微收尾，也被认为替玩家做了新决定；
- 等待鱼儿上钩后，收鱼和听取提示被整体判为越权；
- 修炼或尝试突破时，“瓶颈松动”“准备冲击”“正式冲击”的停止边界反复变化。

保护对象应是新的重大、不可逆选择，而不是所有连续动作。否则正文会被切得过碎，甚至整轮失败。

## P0-F：明确时间意图没有成为提交约束

成功回合的时间没有倒退，但只证明了数值安全，尚未满足叙事一致：

- 本轮成功回合每次只推进 1 至 720 分钟；
- 玩家根据“下月初三收徒”前往等待，系统只推进数小时便在次日清晨开启大典；
- 长期修炼、闭关、赶路与明确日期目前可能被压缩成普通短回合。

时间不需要精确模拟每一分钟，但“片刻、次日、数月、三年”必须保持量级和先后关系一致。

## 当前已经证明有效的保护

本轮并非所有设计都失效，以下基础可以保留：

- 成功回合序号连续，没有重复提交为两个正式回合；
- 世界时间不会倒退；
- 最终失败不会覆盖较新的命卷，也不会写入成功回合；
- 独立审阅能够发现 AI 替玩家决定加入势力、继续突破等越权行为；
- 物品、能力和地点在形成合法实体后，可以跨回合稳定保存。

后续方案应修复“事实来源、行动语义和结构协议”，而不是取消事务、审阅和不可变回合这些已经有效的安全基础。

本批问题的统一实施方案已经固化在
[`v015-trusted-story-pipeline.md`](./v015-trusted-story-pipeline.md)。后续代码、迁移和回放验收必须以该文档为边界，
不得再为单个玩家名称、单个问题编号或单条剧情增加专用裁决分支。

## 统一方案讨论顺序

在开始编码前，依次确定：

1. 角色创建完成时，哪些设定立即成为初始事实；
2. 已提交正文中，哪些内容是长期事实、场景事实、角色认知或纯描写；
3. 推荐选项如何携带来源和引用，保证下一轮可执行；
4. 如何区分事实声明、自由尝试、显式修正和系统查询；
5. 哪些变化需要结构化提交，哪些只属于本轮叙事；
6. 什么才算必须停下等待玩家确认的重大决定；
7. 如何用全部真实样本回放验证，而不是针对单个名字增加规则。
