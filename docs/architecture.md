# 《问仙录》V0.2 Agent 与数据架构

> 文档状态：V0.2 目标架构基线
>
> 配套玩法：`docs/game-design.md`
>
> 原则：V0.2 是独立玩法内核；账号与玩家模型配置可以共享，V0.13 游戏数据只读封存。

## 一、架构目标

V0.2 需要解决的不是“怎样再接一个大模型”，而是四个长期问题：

1. 世界事实不能只存在于聊天上下文；
2. 自由输入必须能够转化为可校验的游戏行动；
3. 人物、时间、地点、物品与事件必须持续演化并可追溯；
4. 模型可以替换和分工，但不能拥有游戏最终裁决权。

架构采用 Java 21、Spring Boot、MySQL 8 的模块化单体。LangChain4j 作为 AI 适配与编排层接入，不进入领域核心。

## 二、系统边界

```text
React H5
  ├─ 展示命卷、人物、纪事与已知世界
  └─ 提交结构化选择或自由行动

Spring Boot V0.2
  ├─ Account：共享账号、会话、额度与玩家密钥
  ├─ Game Application：回合编排、幂等、事务与权限
  ├─ Game Domain：世界、人物、时间、修行、资产、关系与事件规则
  ├─ Content Runtime：正典、地域内容包、事件模板与版本
  ├─ AI Ports：行动理解、故事规划、正文生成与摘要接口
  └─ LangChain4j Adapter：模型供应商、路由、结构化输出与只读工具

MySQL 8
  ├─ 共享账号与模型配置
  ├─ V0.13 只读历史表
  └─ V0.2 独立权威数据表
```

### 2.1 最重要的职责边界

Java 负责：

- 权威事实、领域规则与状态迁移；
- 角色、人物、物品、钱包、时间和地点一致性；
- 战斗与突破的允许范围；
- 事务、幂等、并发、权限和审计；
- 内容版本与命卷实例的持久化。

AI 负责：

- 理解自由行动的语义；
- 在允许范围内提出开放式故事计划；
- 演绎 NPC 的语言、过程和氛围；
- 把已经成立的结果写成小说正文；
- 生成滚动摘要和候选内容。

AI 不得：

- 执行 SQL 或直接调用写数据库工具；
- 绕过 Java 提升境界、增减资产或决定复活；
- 把临时正文描述当作持久事实；
- 访问其他玩家命卷或玩家尚未知道的幕后信息；
- 以模型聊天记忆代替世界状态。

## 三、代码模块

V0.2 后端按领域拆分，仍部署为一个 Spring Boot 应用，避免过早引入微服务复杂度。

V0.2 不在正在运行的 V0.13 目录里原地重写。仓库中新建并行目录，直到灰度完成：

```text
v2/
├─ frontend/          # 新 H5
├─ backend/           # 新游戏后端
├─ admin/
│  ├─ frontend/       # 新管理台
│  └─ backend/        # 独立管理后端
└─ content/           # 世界正典与地域内容包
```

现有 `frontend/`、`backend/` 和 `admin/` 继续代表 V0.13，灰度期间只做阻断性安全修复。这样不会为了开发新框架反复干扰线上玩家，也不需要在一套类中同时兼容两种游戏规则。

```text
com.wenxian.v2
├─ account
├─ game
│  ├─ application
│  ├─ action
│  ├─ world
│  ├─ character
│  ├─ cultivation
│  ├─ conflict
│  ├─ inventory
│  ├─ economy
│  ├─ relationship
│  ├─ location
│  ├─ timeline
│  └─ event
├─ content
├─ narrative
│  ├─ api
│  ├─ context
│  ├─ routing
│  └─ langchain4j
├─ persistence
├─ operations
└─ web
```

模块只通过明确的应用服务和领域接口通信。`narrative.langchain4j` 可以依赖领域层暴露的只读视图，领域层不能反向依赖 LangChain4j、DeepSeek 或任何模型 SDK。

### 3.1 现有资产去留

| 现有资产 | V0.2 决策 | 原因 |
|---|---|---|
| 水墨视觉、日夜主题、字体与自定义弹层 | 迁移并组件化 | 已被玩家验证，具有品牌辨识度 |
| 登录、密码、会话、白名单、公告 | 复用数据与规则，重写接口适配 | 与玩法无关且已经稳定 |
| 玩家密钥加密与脱敏 | 复用安全方案，扩展供应商和模型偏好 | 不能重新冒险实现密钥存储 |
| `Prototype.tsx` 单文件页面 | 不复用结构 | 页面、业务状态和弹层过度集中 |
| `game-api.ts` 手写大型类型 | 改为按领域拆分的类型客户端 | V0.2 资源更多，继续手写容易漂移 |
| `GameState` 大型 JSON 快照 | 只用于旧档读取 | 无法支撑人物历史、关系和事件查询 |
| `DeepSeekGameplayAgentService` | 保留作 V0.13 归档参考，不迁入核心 | 同时承担提示、生成、修复和校验，耦合过重 |
| 当前规则类中的成熟约束 | 提炼测试用例后重新实现 | 规则经验值得保留，旧状态模型不值得继承 |
| 当前管理台巨型 `App.tsx` / `AdminService` | 重写页面和服务分层 | 已无法承载内容、模型路由和领域观测 |
| V0.13 业务表 | 永久只读 | 保留玩家历史，不污染 V0.2 |

### 3.2 前端结构

H5 与管理台均按功能组织，不引入微前端：

```text
src/
├─ app/               # 应用壳、路由、登录态和全局错误
├─ features/          # adventure、character、chronicle、world、settings
├─ components/        # 墨卷基础组件
├─ api/               # 按资源拆分的类型客户端
├─ theme/             # 宣纸、月夜、字号与设计变量
└─ utils/
```

H5 使用 React Router 管理登录、创角、命卷和四个主页面的历史返回；使用服务端状态查询库处理缓存、失效、重试和取消。首版不再额外引入全局状态框架，只有会话、当前命卷和行动草稿使用 React Context 或 reducer。

后端提供 OpenAPI 契约，前端客户端类型由契约生成或在构建中校验，避免 H5、管理台和 Java 各维护一套不一致字段。

## 四、权威数据模型

### 4.1 三层数据

| 层级 | 内容 | 权威来源 |
|---|---|---|
| 世界正典 | 历史、种族、境界、地域骨架、核心势力、世界真相 | 版本化内容包 |
| 命卷实例 | 当前人物、地点状态、事件、资产、关系和知识 | V0.2 领域表 |
| 叙事记录 | 玩家输入、正文、选项、摘要、模型指标 | 回合与叙事表 |

正文不是权威状态。任何只写进正文却没有形成领域变化的“获得、出售、受伤、突破、移动或死亡”都不成立。

### 4.2 当前状态与事件历史并存

采用“当前状态表 + 不可变领域事件”的混合方式：

- 当前状态表用于快速加载角色与场景；
- 领域事件记录每次变化的来源、前值、后值、时间和回合；
- 回合写入时两者在同一事务中完成；
- 调试可以从事件解释当前状态，但正常请求不从第一回合重新播放全部历史。

### 4.3 V0.2 表域

下列是目标表域，不要求一次性把所有细节实现完，但禁止重新回到“全部塞进一个巨大 JSON”的结构。

| 表域 | 主要记录 |
|---|---|
| `v2_game_save` / `v2_world_clock` | 命卷、内容版本、难度、当前时间、状态版本 |
| `v2_character` / `v2_character_state` | 主角与 NPC 的身份、年龄、种族、位置、境界、身体与目标 |
| `v2_relationship` | 身份关系、信任、亲近、敬畏、利益、债务、冲突与共同秘密 |
| `v2_location_definition` / `v2_location_edge` / `v2_save_location_state` | 地点层级、连接、归属、开放状态和命卷内变化 |
| `v2_world_event` / `v2_event_participant` | 事件模板、阶段、期限、参与者、结果与余波 |
| `v2_schedule` | 离场人物与事件的待结算行动 |
| `v2_life_ending` | 玩家确认的归隐、传承等人生结局及其只读摘要 |
| `v2_item_instance` / `v2_inventory` | 唯一物品、堆叠物品、来源、持有者与状态 |
| `v2_wallet` / `v2_wallet_ledger` | 各币种余额、债务与不可变流水 |
| `v2_ability_definition` / `v2_character_ability` | 功法、术法、天赋、技艺及掌握程度 |
| `v2_cultivation` | 当前道路、境界阶段、突破工程和条件缺口 |
| `v2_knowledge` | 世界真相与玩家已知信息的隔离记录 |
| `v2_story_thread` | 当前牵挂、因果债、长期目标与开放线索 |
| `v2_turn_operation` | 已接收、运行中、成功、失败的异步回合任务与恢复位置 |
| `v2_turn` / `v2_domain_change` | 行动、裁决、正文、选项、所有状态变化和问题编号 |
| `v2_story_summary` | 按人物、地点、事件和时间段生成的可替换摘要 |
| `v2_generated_entity` | AI 生成后被正式注册的人物、地点、组织和传承来源 |
| `v2_content_binding` | 命卷绑定的正典与地域内容包版本 |

具名角色必须拥有独立 `v2_character` 记录。再次出现时根据命卷时间和历史变化加载，不从小说正文临时重建。

账号侧另外维护供应商无关的 AI 配置：

- `ai_provider_config`：平台允许的供应商、官方地址、启停和健康状态；
- `ai_model_catalog`：模型代码、展示名、能力、上下文和可用状态；
- `ai_task_route`：行动理解、故事规划、正文和摘要的默认模型与备用模型；
- `user_ai_provider_credential`：按用户和供应商加密保存的密钥；
- `user_ai_preference`：玩家当前选择的凭据来源、供应商和模型；
- `v2_ai_usage_log`：V0.2 每一次真实模型调用的 Token、耗时、结果和所属回合任务；V0.13 的同名旧统计表保持不动。

这些表服务账号和两个版本的运营统计，但 V0.13 不自动获得 V0.2 的新模型路由能力。

### 4.4 统一时间

每份命卷拥有一条独立但统一的世界时间线。这里的“统一”指同一命卷内所有人物和事件使用同一时钟，不表示所有玩家共享 MMO 时间。

时间推进流程：

1. 计算玩家行动实际经过时间；
2. 找出时间窗口内到期的人物日程和事件节点；
3. 依据重要性和玩家相关性进行结算；
4. 更新年龄、位置、状态、事件和价格；
5. 将玩家能够得知的变化转化为书信、传闻、重逢或环境结果。

不为每份离线命卷持续运行后台线程。世界演化在时间推进、重新进入地域或查询相关人物时惰性补算，并保存结算结果。

首版人物日程采用可审计的三段推进：具名 NPC 登场后建立目标日程，时间到期时依次形成“开始推进—已有进展—阶段性结果”。每次结算同时更新人物当前目标、关闭旧日程、按需创建下一段日程，并写入领域变化。它只推进已经落库的目标，不凭空决定隐藏旅行、死亡或关系突变；这些高影响变化仍需后续专门协议。

玩家主动结束人生不经过模型。`POST /api/v2/saves/{saveId}/end` 校验命卷归属、当前状态、运行中任务、结局类型、最低经历回合和角色名确认，随后在同一事务中将角色置为退隐、命卷置为结束并写入 `v2_life_ending`。结束后的命卷只能阅读。

### 4.5 实际状态与玩家知识分离

人物真实境界、事件真实原因和势力计划保存在权威域；玩家已经知道什么保存在知识域。叙事上下文默认只读取玩家知识视图。

调查、传讯、推演和亲历只改变知识状态；它们不一定改变世界真实状态。错误传闻也作为带来源和可信度的知识记录存在。

## 五、内容运行时

### 5.1 内容包

世界正典和地域内容采用版本化 YAML 或 JSON 维护在仓库中，发布时经过校验后导入内容表。内容包包含：

- 种族、境界和通用规则定义；
- 地域、地点连接和势力定义；
- 代表人物原型与固定人物；
- 资源、货币、物品与能力定义；
- 事件模板、触发条件、阶段与余波；
- 可向不同种族展示的线索视图；
- 内容包依赖和兼容版本。

每份命卷绑定内容版本。新增内容可以向后兼容地开放；改变已有规则时必须提供迁移或只应用于新命卷，不能让旧命卷在一次发布后静默换世界。

### 5.2 动态实体注册

AI 可以提出新的路人、小地点、组织、物品或传承。以下任一情况发生后，候选实体必须注册为正式命卷实体：

- 拥有正式姓名并与玩家发生持续关系；
- 持有或交换重要物品；
- 参与正式事件；
- 被玩家承诺、追查、伤害或再次提及；
- 对地点、势力或修行产生持久影响。

注册时生成稳定 ID、类型、来源、时间、地点、核心事实和内容版本。未注册的纯氛围路人不得承担后续关键事实。

### 5.3 事件导演

`EventDirector` 不直接写小说，负责从三类事件线中选择本轮应该显露或推进的事件：

```text
当前时间与地点
+ 玩家人生尺度与目标
+ 到期人物日程
+ 活跃世界事件
+ 未偿因果与近期选择
+ 内容密度限制
→ 本轮事件候选与优先级
```

同一时刻最多突出一个主要压力，其他变化以背景信号出现。事件导演允许玩家错过内容，不通过无限巧合强行把所有事件送到主角面前。

## 六、行动与回合流水线

### 6.1 统一领域对象

```text
PlayerAction
  → ActionIntent
  → DecisionContext
  → ResolutionEnvelope
  → StoryPlan
  → DomainOutcome
  → NarrativeDraft
  → CommittedTurn
```

- `ActionIntent`：玩家想做什么、对象是谁、使用什么、愿意承担什么；
- `DecisionContext`：本轮相关的权威人物、地点、能力、物品、关系与事件；
- `ResolutionEnvelope`：Java 给出的可行结果范围、禁止事项和必须结算的事实；
- `StoryPlan`：在边界内选择过程、人物反应和开放式结果；
- `DomainOutcome`：已经通过规则校验的确定变化；
- `NarrativeDraft`：只负责表达既定结果；
- `CommittedTurn`：正文与全部领域变化原子落库后的正式回合。

### 6.2 按复杂度分路

不是所有回合都走同样数量的模型调用。

#### A. 结构化选择或确定性行动

```text
结构化 Intent → Java 结算 → 一次正文生成 → 校验并提交
```

无需模型重新猜测玩家选择。

#### B. 普通自由行动

```text
一次紧凑调用生成 Intent + StoryPlan + NarrativeDraft
→ Java 校验提案与状态变化
→ 通过后提交
```

若只有结构字段缺失，使用小型结构修复，不重写全文。

#### C. 高影响行动

突破、重要战斗、跨年闭关、建立势力、重大关系变化和世界事件转折使用两阶段流程：

```text
行动理解/计划 → Java 裁决并形成 DomainOutcome → 正文生成 → 提交
```

重要回合可以多一次调用换取一致性，普通回合不承担同样开销。

### 6.3 不成立与需要补充

`REJECTED` 和 `CLARIFY` 是业务结果，不是接口异常：

- 不推进命卷时间和正式回合；
- 不生成无关替代剧情；
- 返回具体原因、冲突事实和可改写建议；
- 原场景和原选项继续有效；
- 不消耗平台赠送回合。

模型故障、网络超时、响应损坏和业务拒绝必须使用不同错误类别。

### 6.4 原子提交

一次成功回合的正文、人物变化、时间、事件、资产、关系、知识和选项必须在同一事务中提交。任一领域变化校验失败，整轮不写入。

使用 `requestId` 防止网络重试重复生成，使用 `stateVersion` 防止旧页面覆盖新状态。同一命卷一次只运行一个正式回合；模型等待期间不占用数据库事务和连接。

普通回合通过受限的 `domainEffects` 协议提交持久变化。模型只能引用本轮上下文中的现有物品、货币、能力、主角和事件，或从当前内容包的可获得物品定义中选择；不能直接调用数据库工具。Java 在提交前校验物品归属、数量、可消耗/可交易状态、钱包余额、交易对价、能力掌握、修炼语义和事件相邻阶段，再在同一事务中写入状态表、物品事件、钱包流水与 `v2_domain_change`。正文中的变化没有合法领域效果就不构成权威事实。

V0.2.0 首个纵向切片覆盖物品获得/消耗/交易移出、钱包收支、已有能力使用、身体状态、修炼感悟和既有事件推进；新人物注册、关系变化、能力学习、相邻境界突破、具备明确危险链的战败死亡已经接入高影响行动协议。复杂势力建立、大规模战争与完整产业链仍留到后续内容包扩展。

### 6.5 单轮会话边界

V0.2 区分四个概念：

- **命卷**：一名角色完整一生的权威数据；
- **游玩会话**：玩家一次打开 H5 的统计与恢复范围；
- **玩家回合**：一次行动从提交到成功写入的完整业务单元；
- **模型调用**：完成一个玩家回合所需的内部请求，可能为零、一次或少量多次。

不使用一个 DeepSeek message ID 串联整份命卷，也不把浏览器在线时长当作记忆。每个玩家回合重新从数据库组装权威上下文，模型响应 ID 只用于诊断。

首版并发规则保持克制：

- 每份命卷最多一个进行中的正式回合；
- 每个账号最多一个正在消耗模型的回合，即使拥有两份命卷；
- 浏览角色、纪事、世界和切换命卷不受限制；
- 重复提交同一 `requestId` 返回原任务，不再次调用模型；
- 管理台以后可以提高账号并发上限，但首版不开放玩家配置。

不对玩家回合设置固定字数或固定 Token 上限。内容长度由场景重要性档案决定；模型档案只设置防失控的安全上界，不能把安全上界当作每章目标。

### 6.6 异步回合任务

提交行动不再让一个 HTTP 请求等待完整生成：

```text
POST 行动
→ 立即创建 v2_turn_operation 并返回 operationId
→ 后端执行理解、裁决、生成、校验和提交
→ H5 通过 SSE 接收阶段状态，连接异常时退回低频状态查询
→ 完成后获取正式回合与最新投影
```

任务状态至少包含 `QUEUED`、`INTERPRETING`、`RESOLVING`、`WRITING`、`COMMITTING`、`SUCCEEDED`、`REJECTED`、`FAILED`。

首版 SSE 只需要发送阶段进度和最终结果，不强制逐字流式正文。浏览器断线、切到后台或重新打开后，通过 `operationId` 查询继续恢复；已经成功的回合直接返回结果，不能重复扣费或重复推进时间。

回合任务失败时保留脱敏诊断和问题编号，但不写入半成品领域变化。服务重启后，尚未开始提交的任务可以安全重试；已经进入提交阶段的任务依靠 `requestId` 与状态版本确认是否完成。纪事使用 `beforeTurn` 游标分页，避免长存档因固定条数上限丢失早期可见记录。

## 七、领域规则执行

### 7.1 规则类型

| 类型 | 示例 | 执行方式 |
|---|---|---|
| 强不变量 | 种族不可静默改变、余额不能透支、死亡不可自动复活 | Java 直接拒绝 |
| 状态机 | 境界相邻迁移、事件阶段、突破工程、人物日程 | Java 状态迁移 |
| 定量规则 | 时间、距离、数量、钱包、年龄、次数 | Java 计算 |
| 约束范围 | 越级战斗、关系反应、制作质量、开放式探索 | Java 边界 + AI 计划 |
| 纯表达 | 环境、对话、节奏、心理与文学语言 | AI 生成 |

### 7.2 不使用关键词补丁做核心裁决

“元婴”“打败”“卖掉”等词不能直接决定玩家意图与结果。自由输入先转成结构化意图，再与权威实体绑定。关键词只允许用于安全门控、明显垃圾输入和性能优化，不能承担世界规则判断。

### 7.3 语义实体绑定

行动中的“师父”“那块矿石”“刚才的剑诀”等表达按以下顺序解析：

1. 当前场景中明确可见或近期提及实体；
2. 玩家已知实体的别名、关系称谓和稳定名称；
3. 语义检索得到的少量候选；
4. AI 在候选集合中选择；
5. 仍有歧义则要求玩家补充。

AI 不能凭空提交数据库 ID，也不能用相似名称静默绑定错误实体。

## 八、AI 服务层

### 8.1 自有接口优先

领域与应用层只依赖自己的接口：

```java
public interface IntentInterpreter {
    ActionIntent interpret(IntentRequest request);
}

public interface StoryPlanner {
    StoryPlan plan(PlanningRequest request);
}

public interface NarrativeWriter {
    NarrativeDraft write(NarrativeRequest request);
}

public interface StorySummarizer {
    StorySummary summarize(SummaryRequest request);
}
```

LangChain4j 实现这些接口，但 LangChain4j 的类型不得出现在游戏领域对象中。未来更换 Spring AI 或直接 SDK 时，只替换适配层。

### 8.2 LangChain4j 的职责

- 用 AI Services 表达任务接口和结构化返回；
- 接入 DeepSeek 及其他模型供应商；
- 处理流式输出、超时和基础重试；
- 暴露受限只读工具；
- 返回 Token、完成原因、工具调用与供应商元数据；
- 为摘要、检索和内容候选提供统一调用方式。

不采用会自主无限循环的通用 Agent。工具循环、重试次数和模型调用次数由应用层明确控制。

### 8.3 模型路由

模型不按“全站只有一个当前模型”配置，而按任务配置模型档案：

| 任务 | 主要关注 |
|---|---|
| 行动理解 | 速度、结构化输出、低成本 |
| 故事规划 | 推理、规则遵循、人物一致性 |
| 正文生成 | 中文叙事质量、长文本稳定性 |
| 摘要压缩 | 成本、事实保留 |
| 内容审核 | 稳定分类、低成本 |

`ModelRouter` 根据任务类型、玩家密钥、模型能力、健康状态和运营配置选择供应商。切换供应商不能改变领域协议。

每个模型维护能力清单：结构化输出、工具调用、上下文长度、流式能力和已验证版本。不能假设所有 OpenAI 兼容模型行为完全一致。

供应商适配只实现一个最小边界：接收统一 `ModelRequest`，返回统一 `ModelResult`，并报告自身支持的模型能力。DeepSeek、未来其他厂商或直接 SDK 都是该边界的实现；业务层不拼供应商 URL，也不读取供应商专属响应字段。

V0.2.0 只对玩家开放 DeepSeek Flash 与 DeepSeek Pro，先把模型抽象做正确，不同时接入大量未经验证的供应商：

- Flash 是平台默认模型，运营可在管理台按任务调整平台路由；
- 玩家使用自己的 DeepSeek 密钥时，可以在 Flash 与 Pro 之间选择；
- 凭据来源和自备密钥模型偏好按账号保存，从下一次回合任务生效；
- 每个回合记录实际供应商、模型和凭据来源，历史显示不随之后切换而改变；
- 如果所选模型停用或密钥不支持，明确要求重新选择，不静默改用更贵模型。

内部任务路由与玩家选择保持简单：使用平台额度时，管理台为不同任务配置 Flash 或 Pro，H5 只展示本轮实际模型；使用玩家密钥时，行动理解、规划和正文默认都使用玩家选择的模型，摘要优先延后或使用同一密钥的 Flash。首版不向玩家暴露“每个内部任务选一个模型”的复杂配置。

### 8.4 玩家自备密钥

共享账号层的密钥记录扩展为供应商维度。现有 DeepSeek 密钥迁移为 `DEEPSEEK` 供应商记录。V0.2 初期只允许平台明确支持的供应商和固定官方地址，不接受玩家任意填写请求地址，避免服务端请求伪造和密钥泄露。

密钥使用独立主密钥进行 AES-256-GCM 加密，只在调用瞬间于服务端解密；接口只返回供应商、是否启用、尾号和验证时间。删除账号时级联删除密钥。

玩家密钥只替换调用凭据，不绕过游戏规则、内容版本和回合并发限制。

玩家可通过以下三个动作管理自己的推演配置：验证并保存密钥、选择 Flash 或 Pro、删除密钥并回到平台模式。保存后只展示尾号；复制、刷新和重新登录都不能取回明文。

### 8.5 降级策略

- 同一供应商短暂失败：有限次数重试，使用退避；
- 当前模型不可用：只有配置了兼容备用模型时才降级；
- 玩家密钥失败：不擅自改用平台付费密钥，明确提示玩家；
- 正文生成失败：命卷不提交，玩家可以重试同一 `requestId`；
- 摘要失败：延后异步补做，不阻断正式回合；
- 结构修复：只修复结构，不重新生成整篇正文。

## 九、上下文与长期记忆

### 9.1 数据库是真实记忆

LangChain4j ChatMemory 或模型 message ID 只用于一次任务内的语言连续，不承担长期命卷状态。长期记忆来自领域表、事件、知识和摘要。

### 9.2 Context Assembler

每次调用按优先级组装上下文：

1. 本轮不可缺少的世界规则与输出协议；
2. 当前场景、玩家行动和相关实体完整事实；
3. 活跃事件、人物关系和本轮必须结算的时间变化；
4. 上一章与近期关键事件；
5. 更早历史的按实体摘要；
6. 低相关背景索引。

不设置脱离模型能力的固定 5,500 Token 硬上限。每个模型档案配置可用上下文比例，组装器按优先级裁剪；最关键的领域事实永远不能为保留文学前情而被裁掉。

### 9.3 摘要不是一段总传记

摘要按人物、地点、势力、事件、修行道路和时间段分别维护。修改某个人物时，只重算相关摘要。模型需要追查旧事时先检索实体与事件，再读取对应摘要或原始回合。

向量检索用于召回可能相关的历史，不作为权威判断。检索结果必须回到结构化实体与事件记录确认，不能因为语义相似就创造事实。

## 十、只读工具

LangChain4j 工具仅提供当前命卷、当前玩家知识范围内的读取能力，例如：

- `get_character_facts`
- `get_relationship_context`
- `get_location_facts`
- `get_active_events`
- `get_inventory_and_wallet`
- `get_abilities_and_cultivation`
- `get_known_history`
- `search_known_entities`

所有工具由服务端隐式绑定 `userId`、`saveId`、知识边界和最大返回量。模型不能传入其他玩家 ID，也不能调用通用 SQL。

状态变化通过 `StoryPlan` 和 `DomainOutcome` 协议提出，由 Java 执行；不提供 `add_item`、`update_realm`、`kill_character` 等直接写工具。

## 十一、接口与 H5

### 11.1 H5 信息架构

H5 保持历练、角色、纪事、世界四个底部页面，但重写内部结构：

| 页面 | 首屏 | 深入内容 |
|---|---|---|
| 历练 | 当前场景、正文、选项、行动框 | 裁决说明、事件进度、回合恢复 |
| 角色 | 身份、种族境界、修炼道路、当前身体 | 天赋功法、职业、资产、物品、人间锚 |
| 纪事 | 最近重要变化与统一时间 | 按人物、关系、事件、突破和年份筛选 |
| 世界 | 已知区域、当前位置、活跃大事 | 地点、势力、人物、线索与可到达方向 |

顶部提供命卷入口和卷外设置。命卷入口负责切换 V0.2 角色与查看 V0.13 只读档案；卷外设置负责账号、主题、字号、公告、平台额度和推演模型。模型设置不再挤在世界页，也不新增第五个底部页面。

角色、纪事与世界页默认是阅读与检索视图，不提供会额外消耗一个回合的“使用、修炼、出售”按钮。改变命卷的行为统一从历练页行动框或当前场景选项发起；账号、阅读外观和模型设置不计入游戏行动。

### 11.2 前端数据边界

H5 不维护可写的本地游戏副本。服务器投影是页面唯一事实，本地只缓存最近一次成功读取的数据用于弱网只读展示。

- 当前命卷切换后，所有资源查询都显式携带新 `saveId`；
- 成功回合按服务端返回的失效范围刷新页面，不重新请求全部世界；
- 行动草稿按命卷保存，不能串到另一角色；
- 页面展示的回合、时间和模型必须来自当前命卷或当前任务；
- 离线时禁止提交行动，但允许阅读缓存内容。

### 11.3 API 分组

V0.2 游戏资源统一使用 `/api/v2/`，与 V0.13 `/api/v1/` 并存。首批接口按资源分组：

```text
/api/v2/auth/*                         账号登录、退出与当前用户
/api/v2/bootstrap                      版本、公告、命卷摘要与模型偏好
/api/v2/saves                          创建和列出 V0.2 命卷
/api/v2/saves/{saveId}                 命卷摘要、封存与结局确认
/api/v2/saves/{saveId}/creation/*      创角、命格与天赋
/api/v2/saves/{saveId}/scene           当前历练投影
/api/v2/saves/{saveId}/character       角色投影
/api/v2/saves/{saveId}/chronicle       纪事分页与筛选
/api/v2/saves/{saveId}/world           已知世界投影
/api/v2/saves/{saveId}/actions         提交行动并创建回合任务
/api/v2/turn-operations/{operationId}  查询任务状态与最终结果
/api/v2/turn-operations/{operationId}/events  SSE 进度
/api/v2/ai/providers                   玩家可选供应商与模型
/api/v2/ai/preference                  当前凭据来源和模型选择
/api/v2/ai/credentials/{provider}      验证、保存与删除玩家密钥
/api/v2/legacy-archives/*               V0.13 只读命卷档案
```

所有写接口携带 `requestId`，涉及命卷状态的写接口同时携带 `expectedStateVersion`。响应返回新的状态版本、内容版本和需要刷新的投影列表。

业务拒绝使用结构化业务响应，包含稳定编码、世界观内说明、冲突事实、建议、是否消耗回合和状态是否变化。技术异常使用统一错误协议并返回可查询的问题编号，不向玩家展示 Java、LangChain4j、模型供应商内部错误或数据库细节。

### 11.4 不在首版实现

- 不做玩家自定义任意 API Base URL；
- 不做每个任务分别选择模型的专家模式；
- 不做多模型投票和模型互相辩论；
- 不做浏览器内本地规则引擎；
- 不做完整离线游玩；
- 不做复杂三维或自由拖拽地图；
- 不为了架构形式拆成微服务。

## 十二、V0.2 管理台

### 12.1 产品目标

管理台不是数据库表格浏览器，而是让运营快速回答四个问题：游戏现在是否正常、玩家为什么卡住、哪套内容正在生效、模型花费和质量是否合理。

保留独立管理前端和管理员会话。管理接口统一置于 `/api/v2/admin` 并使用独立 Bearer 会话鉴权，不复用玩家 Cookie；首版与 V0.2 游戏服务同进程部署，减少灰度期的运维复杂度，后续只有在负载或权限边界需要时再拆成独立服务。V0.2 不继续向旧版单文件页面追加功能。

### 12.2 七个一级页面

1. **总览**：在线与活跃账号、回合成功率、错误率、模型成本、延迟、卡住任务和版本；
2. **玩家**：邮箱筛选、账号、V0.2 命卷、V0.13 档案、模型偏好、近期回合和问题记录；
3. **内容**：内容包版本、青岐州开放状态、导入校验、命卷绑定数量和回滚信息；
4. **模型**：供应商、Flash/Pro、平台密钥、任务路由、健康检测、Token 与延迟；
5. **运营规则**：赠送回合、在世命卷上限、自备密钥开关和额度提示；
6. **问题诊断**：进行中与失败的回合任务、问题编号、领域校验错误和安全终止；
7. **发布管理**：版本公告、登录页展示、进入后弹出、灰度白名单和动态维护提示。

管理员账号与操作审计放入发布页的安全分区或账号菜单，首版不单独占一级导航。

### 12.3 内容管理首版边界

内容创作仍在仓库中的版本化 SQL/YAML/JSON 完成。管理台首版只提供：

- 查看当前内容包版本、状态和发布时间；
- 查看已经装载的地点、物品、能力与事件模板数量；
- 通过 Flyway 和自动化测试校验内容引用后随正式版本发布。

首版不在管理台上传、发布或回滚内容包，也不建设在线世界编辑器、流程画布或可视化规则编程器。内容版本回滚随代码与数据库迁移统一执行，避免运营界面绕过领域校验直接修改正典。

### 12.4 模型管理

管理台按“供应商—模型—任务路由”展示，不再只有一个全局切换按钮：

- 启用或停用 Flash、Pro；
- 分别配置命格生成与回合推演等任务的默认及备用模型；
- 在总览查看平台和玩家调用合计的 Token 与平均延迟；
- 在玩家详情查看凭据来源、验证状态和掩码尾号，但绝不回传玩家密钥明文。

平台密钥仍由服务器环境变量维护，管理台不接收或回显平台密钥；模型健康验证、启停及受影响账号检查在扩大灰度前补充，不阻塞 V0.2.0 的小范围试玩。

首版不允许管理台随意输入未登记供应商地址。增加供应商需要代码适配、能力验证和正式发布。

### 12.5 玩家与回合诊断

玩家详情同时展示账号层与命卷层信息：

- 当前 V0.2 命卷、已封存结局和 V0.13 旧档；
- 当前模型、凭据来源、尾号和最近验证状态；
- 活跃人物、地点、事件、境界工程和资产摘要；
- 回合任务阶段、模型调用、领域变化与最终正文；
- 业务拒绝原因、技术错误和可复制的问题编号。

管理员可以调整全局运营额度与命卷上限、加入灰度白名单和终止尚未提交的卡死任务；首版不在管理台重置密码或手工解锁账号，也不能手工编辑玩家境界、钱包或物品。需要修复账号或权威游戏数据时使用经过审计的迁移脚本，而不是管理台随意改字段。

## 十三、版本与旧数据策略

### 13.1 共享内容

V0.13 与 V0.2 只共享：

- `app_user` 账号与认证；
- 会话与安全控制；
- 玩家自备模型凭据；
- 必要的运营配置和公告能力。

共享不意味着两个版本共用角色表或游戏规则。

### 13.2 旧版冻结

- V0.13 后端进入只读档案模式后停止玩法修复；
- 原有 `game_save`、`game_turn`、`game_life_archive` 等表不迁入 V0.2；
- 旧角色通过只读接口查看，不允许继续写入；
- V0.2 表统一使用 `v2_` 前缀，迁移脚本不得修改旧角色事实；
- V0.2 独立测试地址验证稳定后再切换正式入口。

### 13.3 内容版本

每份 V0.2 命卷记录引擎版本与内容包版本。规则热修、内容新增和结构迁移分别管理，避免把“发一条新剧情”与“改变世界规律”混成一次不可追溯更新。

## 十四、可靠性与可观测性

每次 AI 调用记录：任务类型、供应商、模型、平台或玩家密钥来源、输入输出 Token、缓存 Token、延迟、结果、重试和完成原因。每次回合记录阶段耗时：加载、理解、裁决、生成、校验、提交。

运营指标至少包括：

- 回合成功率、业务拒绝率和技术失败率；
- P50、P90、P99 总耗时及各阶段耗时；
- 每成功回合平均 Token 与成本；
- 结构修复率和全文重试率；
- 人物、地点、境界、资产与时间一致性错误；
- 玩家在 1、5、20、100 回合的留存与结局分布。

日志和问题记录必须脱敏，不保存密码、完整 API Key 或模型请求中的敏感账号信息。

### 14.1 玩家行为回归测试

长线测试分为三层，不能用单一的“跑了一千回”代替：

1. **确定性耐久层**：重复等待和跨年，验证统一时钟、回合审计、分页及长期存储；
2. **玩家行为领域层**：读取脱敏的 V0.13 聚合行动画像，按真实权重混合调查、互动、赶路、修炼、等待、能力、战斗、物品、其他和交易，走正式权威上下文、Java 裁决、提案规范化、领域校验、事务提交和数据库读取；
3. **真实模型层**：使用平台当前启用模型生成代表性行动，验证模型输出仍能被同一领域边界接住，并记录 Token、延迟和外部服务故障。

历史画像只保存总量、分布、抽样方法和测试目标，不保存原始玩家文本或账号。当前基线来自 V0.13 在 2026 年 8 月 3 日的 42,547 回合只读快照：精确识别 34,014 次选项点击，对 1,000 条非点击行动和 1,000 条旧式未标注选项做匿名语义抽样。投影是测试权重，不作为精确运营统计或个体玩家画像。

三族混合一千回测试必须核对：每类行动实际执行数、三套境界相邻晋升、人物与关系持续性、能力学习与使用、背包增减、钱包流水守恒、价格校验、地图直连、长期时间推进，以及所有拒绝场景失败不改档。真实模型故障属于验收结果的一部分；例如供应商连接失败时，本轮必须明确拒绝且保持存档不变，重试成功不能掩盖首次故障。

## 十五、部署与数据安全

当前公网入口保持不变：香港 Nginx 提供 `wenxianlu.cn` H5 与 HTTPS，`/api/` 转发至京东云后端，权威数据库为阿里云 RDS MySQL 8。私钥、数据库密码和模型密钥只保存在服务器外置配置或环境变量中。

V0.2 在独立后端端口、独立 H5 构建目录和独立测试入口部署。首轮灰度只开放白名单账号。数据库迁移顺序为：备份、创建 V0.2 新表、导入内容包、运行只读一致性检查、启动 V0.2、测试账号验证；不停止或改写 V0.13 表即可完成前期并行验证。

版本分支采用三线管理：`V0.13` 永久保留旧版，`V0.2` 承载新版本开发与灰度，`master` 只指向已经正式验证通过的稳定版本。当前 `main` 在三条目标分支创建、核对和推送完成前保留。V0.2 正式上线时，将通过验证的 `V0.2` 提交合并或快进到 `master` 并打版本标签，不通过反复重命名分支模拟发布。

## 十六、V0.2.0 实施边界

V0.2.0 要把可长期扩展的骨架做实，但不一次建完未来所有系统。开发内容分为三层。

### 16.1 首版必须落地

- 建立并行的 `v2/frontend`、`v2/backend`、`v2/admin` 与 `v2/content`，不在 V0.13 代码中继续扩建玩法；
- 接通共享账号、会话、白名单、公告、额度和玩家密钥，并提供 V0.13 档案只读入口；
- 完成人物、统一时间、地点、事件、关系、知识、修行、能力、物品、钱包和回合的最小权威模型；
- 导入青岐州首个内容包，走通三族创角、生活、移动、交易、修炼、冲突、跨时段行动和人生结束；
- 实现异步回合任务、幂等、状态版本、阶段 SSE、断线恢复和原子提交；
- 建立自有 AI Ports、LangChain4j 适配层、上下文组装器和用量记录；
- 只接入 DeepSeek 官方 Flash 与 Pro，支持平台凭据和玩家自备凭据，允许玩家按账号切换模型；
- 重做四页 H5、创角与卷外设置，迁移现有水墨主题、字号、公告和自定义弹层；
- 重做管理台的总览、玩家、内容、模型、运营规则、问题诊断和发布管理七页，优先保证诊断与灰度发布可用。

### 16.2 首版只预留契约

- 供应商、模型能力和任务路由使用中立接口与表结构，但不为未接入模型编写假适配器；
- 语义检索保留 `EntityRetriever` 接口，首版先用稳定 ID、别名、关系和结构化查询，不强制部署向量数据库；
- SSE 协议保留正文增量事件，首版只发送阶段和最终结果；
- 内容包支持地域依赖与版本兼容，首版只发布玄墟界正典和青岐州；
- 事件导演允许未来扩展大域事件，首版只结算与当前命卷相关的区域事件和人物日程；
- 模型档案允许未来增加供应商，玩家界面首版只显示已经验证的 Flash 与 Pro。

### 16.3 明确延后

- DeepSeek 之外的正式供应商适配；
- 玩家自定义任意 API 地址与兼容模型；
- 多模型投票、模型辩论和自主循环 Agent；
- 逐字正文流式、多个命卷同时生成和玩家自定义任务路由；
- 独立向量数据库、知识图谱平台和全量历史向量化；
- 在线世界编辑器、可视化规则编排和微服务拆分；
- 复杂战力评分、完整制作产业链与大域级战争模拟。

判断一项新能力是否应进入 V0.2.0，只看三个条件：是否支撑首发核心循环、是否解决已经验证的玩家问题、是否会成为后续内容扩展的硬阻塞。仅仅“以后可能有用”不足以进入首版。

## 十七、实施顺序

### 阶段 0：冻结边界

- 确认 V0.13 只读归档策略；
- 锁定 V0.2 总纲、领域对象和内容包格式；
- 建立 V0.2 独立模块和数据库迁移基线。

### 阶段 1：无 AI 领域内核

- 完成人物、时间、地点、物品、钱包、关系、修行和事件状态机；
- 用固定测试数据走通创角、移动、交易、修炼、时间推进和死亡；
- 验证所有变化可以追溯到领域事件。

### 阶段 2：内容运行时

- 导入青岐州内容包；
- 实现动态实体注册、事件导演和离场人物演化；
- 不调用模型也能产生合法的事件候选与结算边界。

### 阶段 3：LangChain4j 接入

- 实现自有 AI Ports 与 LangChain4j 适配器；
- 接入至少一个主模型和一个经过验证的备用模型；
- 完成结构化返回、任务路由、只读工具、上下文组装和用量记录。

### 阶段 4：叙事与 H5

- 把领域结果转为小说章节、选项和四页投影；
- 验证手机端流式阅读、错误恢复与命卷切换；
- 进行 20 回合真实模型体验测试、长存档投影与分页测试，以及 1,000 次领域演化、跨十年与角色死亡的自动化长跑测试。
- 发布验收必须使用平台真实模型跑完整链路；`mvn test`保留无 Token 的领域回归，`mvn -Preal-model test`同时执行领域回归与真实模型场景，且缺少`V2_AI_PLATFORM_API_KEY`时必须失败。任何影响玩家剧情、裁决或时间推进的改动，若没有对应真实模型用例，不视为验收完成。

### 阶段 5：灰度验证

- 独立测试入口与白名单；
- 使用全新 V0.2 命卷测试，不兼容旧角色；
- 先验证一致性和长期循环，再扩大玩家范围。

V0.2 不从“把现有 DeepSeek 类换成 LangChain4j”开始，而从无 AI 领域内核开始。只有领域结果已经可校验，模型多样化才会真正提升体验，而不是让错误来源从一个模型变成多个模型。
