# 《问仙录》当前产品方向

> 当前有效方向：多世界、轻状态、强记忆的 AI 修仙叙事游戏
> 最近更新：2026-08-08

本文件只记录当前产品决策。具体玩法以 `docs/game-design.md` 为准，技术边界与迁移顺序以 `docs/architecture.md` 为准，表结构和字段含义以 `docs/data-dictionary.md` 为准，已经交付的版本内容以 `docs/version-history.md` 为准。

## 1. 产品定位

《问仙录》首先是一款允许玩家自由行动的单机 AI 修仙叙事游戏，不是依靠完整数值、固定地图和预制章节驱动的传统文字 RPG。

长期目标只有三项：

1. 玩家可以自由描述行动，剧情保持连贯并具有修仙代入感；
2. 时间、地点、境界、物品、能力和重要人物等已经发生的事实能够长期一致；
3. 平台模型与玩家自备模型可以安全、稳定地驱动同一套游戏流程。

世界观负责提供修仙题材、种族和因果边界，不为所有玩家规定相同出身、相同成长速度、固定主线或唯一结局。

## 2. 当前玩法引擎

当前正式玩法使用“轻叙事引擎”。产品发布版本与玩法引擎必须分离：V0.15、V0.16 等产品发版默认继续使用同一引擎，不能因为发布新版本就复制一套代码、API和数据表。

当前引擎坚持：

- 推荐行动与自由输入并存；
- Agent 负责理解行动、生成过程和判断局部结果；
- Java 只保护账号、幂等、并发、时间、生命周期、密钥和原子落库等系统边界；
- 当前事实与历史记录分开保存，Prompt 只加载本轮相关内容；
- 物品、能力和重要人物允许由 Agent 自由生成，但获得、变化和移除必须长期一致。

## 3. V0.2 方案状态

V0.2 的“传统文字 RPG 底座 + 大模型自由叙事”方案正式标记为**废弃方案**，不再作为当前路线或默认后续版本计划。

废弃原因：

- 完整战力、经济、职业、地图、事件和长期内容生产体系超出当前单人开发能力；
- 不完整的强规则比没有规则更容易制造裁决冲突和玩家体验问题；
- 为规则补齐大量内容会显著拖慢玩法验证和版本迭代；
- 玩家反馈更需要自由行动、剧情连贯和记录一致，而不是复杂数值系统。

V0.2 代码和设计只作为历史实验封存。当前 H5 可以复用其中已经验证过的视觉外壳和通用交互，但不继承其战力、经济、职业、固定地图或内容生产体系。

## 4. 明确不做的内容

当前方向不建设：

- 精密战力公式、伤害公式和自动胜负计算；
- 全世界统一物价表、复杂经济模拟和装备数值体系；
- 固定职业树、庞大技能树和必须按顺序解锁的成长路线；
- 为支撑数百回合而预制数百章主线；
- 依靠大量 Java 关键词和硬编码规则裁决玩家想象力；
- 唯一通关结局或所有玩家共享的固定成长节奏。

这些内容不是“稍后一定开发”的待办。只有真实玩家数据证明某个局部规则不可缺少时，才以最小范围单独立项。

## 5. 版本与数据原则

项目必须区分四类版本：

| 类型 | 示例 | 用途 |
|---|---|---|
| 产品发布版本 | `V0.15` | 公告、展示、灰度和运营统计 |
| 故事引擎 | `LIGHT_NARRATIVE` | 选择一套玩法逻辑 |
| 引擎版本 | `1`、`2` | 同一玩法逻辑发生重大变化 |
| 存档结构版本 | `1`、`2`、`3` | 升级当前状态 JSON 的结构 |

Prompt 另有独立版本，用于比较上下文、成本和生成质量。

禁止继续新增：

- `V015GameService` 等以产品版本命名的业务类；
- `/api/v1/v015/*` 等以产品版本命名的稳定接口；
- `v015_game_save` 等以产品版本命名的新业务表；
- H5 中 `v014 ? ... : v015 ? ...` 一类长期分支。

只有新增稳定业务实体时才能新增表，表名必须按业务能力命名，而不是按产品版本命名。

## 6. 历史命卷策略

- V0.14 命卷完整迁入统一命卷平台，迁移后原表冻结为只读回滚源；
- V0.13 命卷作为“旧世档案”统一展示，默认只读；
- 玩家可以从 V0.13 档案“承接旧世”，系统复制可靠事实创建新命卷，不覆盖原档；
- 旧体力、追查、旧裁决和异常数值不进入当前引擎；
- 迁移和承接必须留有来源、哈希、状态和失败记录。

## 7. 新功能准入

任何新功能进入开发前必须回答：

1. 它属于哪个业务领域；
2. 哪张表或哪个服务是权威数据源；
3. 会改变哪些状态；
4. 是否真的需要新表；
5. 是否影响已有命卷；
6. 旧存档如何升级或保持兼容；
7. Agent、Java 和 H5 分别负责什么；
8. 失败时如何回滚；
9. 管理台如何观察；
10. 如何用真实 RDS、真实模型和手机 H5 验证。

上述问题未确认前，不开始业务实现。

## 8. 当前改造方向

当前版本继续稳定运行；普通新功能暂停，线上只接受独立、可回滚的 P0 Hotfix。架构改造按以下顺序推进：

1. 建立统一 Story API 和领域服务，底层暂时读取 V0.14 表；
2. H5 切换稳定接口，移除产品版本判断；
3. 建立 `story_*` 通用表并完整迁移 V0.14；
4. 管理台改为按发布、引擎、Prompt 和模型筛选；
5. 接入 V0.13 旧世档案与承接能力；
6. 稳定后停用版本化接口，旧表继续保留只读。

这次改造不是重新设计玩法，而是为已经验证的轻叙事玩法建立可持续维护的技术底座。
