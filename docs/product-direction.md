# 《问仙录》当前产品方向

> 当前有效方向：玩家主导、动态世界、可信记忆的 AI 修仙互动叙事
> 最近更新：2026-08-09

本文件只记录当前产品决策。具体玩法以 `docs/game-design.md` 为准，技术边界以 `docs/architecture.md` 为准，表结构和字段含义以 `docs/data-dictionary.md` 为准，已经交付的版本内容以 `docs/version-history.md` 为准。

## 1. 产品定位

《问仙录》不是让 AI 自动续写小说，也不是依靠完整数值、固定地图和预制章节驱动的传统文字 RPG。它是一种由玩家持续作出行动、AI 演绎过程、系统保存真实经历的单机修仙互动叙事。

当前产品承诺只有三条：

1. **你的经历不会被遗忘。** 已经确认的人物、物品、能力、时间和事件能够在后续被正确取回；
2. **你的决定不会被代替。** AI 可以描写执行过程和直接后果，但不能替玩家完成新的重大、不可逆决定；
3. **你确认的事实不会被 AI 随意改写。** 世界允许成长和修订，但任何冲突变化都必须有明确来源并留下记录。

这三条优先于篇幅、文采、玩法数量、战力精度和生成速度，是后续功能是否进入开发的首要判断标准。

## 2. 谁服务谁

系统各部分的关系必须保持清晰：

- 玩家的长期代入与自主选择是最终目标；
- 玩法规则服务于玩家自主性，不以限制自由为目的；
- Agent 服务于理解行动、演绎过程和扩展内容；
- 世界与事实系统服务于连续性、可追溯性和信任；
- 数据库保存已经发生和已经确认的内容；
- H5 提供行动、阅读、查看和修正入口；
- 管理台服务运营、观察、灰度和问题定位，不参与剧情裁决。

不能让玩家服务于规则，也不能让数据库迁就模型临时生成的文本。

## 3. 世界设计原则

世界采用“**软起点 + 动态强事实 + 玩家可修订**”，不是所有命卷共享一套不可改变的强设定。

### 系统硬规则

系统硬规则只保护产品承诺和数据安全，例如玩家决策边界、身份与生命周期、统一时间、物品归属、能力掌握状态、幂等与审计。玩家和 AI 都不能通过普通剧情静默绕过这些规则。

### 当前世界事实

所选世界模板、创角设定以及游玩过程中被确认的世界规则，共同形成该命卷的“当前世界事实”。Agent 后续必须遵守，但玩家可以明确要求扩展、转变或修订。

### 未定义空间

没有被设定的宗门、地域、修炼方式、族群关系和历史保持开放。玩家可以自由创造，AI 也可以在不冲突的前提下补充，不要求预先建立完整世界书。

“玄墟界”“绝天之变”“东陆九州”等内容是可选开局模板，不是《问仙录》所有命卷的永久宇宙真相。H5 的完整自定世界入口可暂时置灰，但玩家仍可在对话中逐步塑造当前世界。

## 4. 当前玩法引擎

当前正式玩法继续使用“轻叙事引擎”。产品发布版本与玩法引擎分离：V0.15、V0.16 等产品发版默认复用同一套代码、API 和数据表。

当前引擎坚持：

- 推荐行动与自由输入并存；
- Agent 判断开放叙事中的局部过程，Java 不建立庞大关键词裁决；
- 一次回合完成玩家已经提交的行动及其直接结果，在下一项重大决定前停下；
- 当前事实、人物认知、历史回合和叙事正文分开管理；
- 物品、能力、人物和世界设定允许动态生成，但正式变化必须可追溯；
- 纠错不是重写聊天记录，而是生成新的有效事实并保留旧记录。

## 5. V0.15 的设计目标

V0.15 不先增加更多玩法按钮，而是建立一条可信的回合闭环：

```text
玩家行动
→ 读取相关事实与记忆
→ Agent 生成剧情和变化提案
→ 系统检查通用边界
→ 原子保存事实、实体、记忆和回合
→ 玩家查看、继续或修正
```

可信闭环不等于把每一句正文和每一个场景名词都变成数据库实体。V0.15 采用“事实写入严格、剧情推进宽松”：

- 玩家直接声称已经拥有物品、掌握能力或建立关系时，必须有当前可信事实支持；
- 玩家寻找、学习、自创、交谈、探索等尚未发生的尝试默认允许，结果由本轮提案裁定；
- 普通路人、摊主、溪水、街道和身体部位属于本轮临时叙事对象，不要求稳定 ID，也不进入角色、背包或地标档案；
- 临时对象一旦接收物品、形成长期关系、发生生死变化或成为持续线索，才晋升为长期实体；
- 每轮先明确成功、部分成功或失败，再保存真正需要跨回合保持的变化。正文不得宣布计划中没有落定的能力、物品、关系或境界结果。

系统保护的是已经提交的长期事实，不负责许可普通剧情能否发生。结构或审阅的不确定性只有在可能污染长期事实时才阻止提交，不能因为普通场景对象没有数据库 ID 而卡住问路、观察或交谈。

第一批必须证明的场景：

1. 已死亡的重要人物不会无缘无故复活；
2. 已掌握且未失去的能力不会突然变成“尚未掌握”；
3. 明确数量的物品在获得、使用、赠予、出售后保持一致；
4. 玩家明确闭关或赶路的时间能正确进入统一时间线；
5. AI 不替玩家完成离开、效忠、杀戮、牺牲等新的重大决定；
6. 玩家对事实或世界设定的修正会持续生效并留下审计记录。

这些场景通过真实玩家回放、真实 RDS 和真实模型验证后，再进入业务编码和发布阶段。

## 6. V0.2 方案状态

V0.2 的“传统文字 RPG 底座 + 大模型自由叙事”方案正式标记为**废弃方案**，不再作为当前路线或默认后续版本计划。

废弃原因：

- 完整战力、经济、职业、地图、事件和长期内容生产体系超出当前单人开发能力；
- 不完整的强规则比没有规则更容易制造裁决冲突；
- 为规则补齐大量内容会显著拖慢玩法验证；
- 玩家当前最在意的是自由行动、决定权和事实一致，而不是复杂数值。

V0.2 代码和设计只作为历史实验封存。当前 H5 可以复用已验证的视觉外壳和通用交互，但不继承其战力、经济、职业、固定地图或内容生产体系。

## 7. 明确暂不建设

- 精密战力、伤害公式和自动胜负计算；
- 全世界统一物价、复杂经济模拟和装备数值体系；
- 固定职业树、庞大技能树和强制成长路线；
- 为支撑长线游玩而预制数百章主线；
- 后台持续运行所有 NPC 的高成本世界模拟；
- 依靠大量 Java 关键词、种族词表和固定内容白名单裁决开放输入；
- 把向量数据库当成事实一致性的替代品；
- 完整世界编辑器、世界 MOD 市场和跨世界联机；
- 唯一通关结局或所有玩家共享的固定成长节奏。

这些内容只有在当前可信闭环稳定、玩家数据证明必要且能独立验收时，才重新立项。

## 8. 版本、数据与历史命卷

项目继续区分产品发布版本、故事引擎、引擎版本、存档结构版本和 Prompt 版本。禁止以产品版本命名新的业务类、稳定接口和业务表。

- V0.14 命卷已经迁入统一命卷平台，原表只作为回滚源；
- V0.13 早期测试数据只供内部排查，H5 不展示、不承接，也不占用当前命卷槽位；
- V0.15 产品与事实模型设计不强制迁移线上命卷；
- 未验证的数据结构先在独立测试命卷灰度，禁止直接批量重写玩家历史；
- 低活跃账号不因“清理统计”直接删除，账号与命卷生命周期需另行制定可告知、可撤销、可匿名化的规则。

## 9. 用户与数据生命周期

账号注册、低活跃、命卷删除与注销必须和运营统计分开处理：

- 注册后只玩 2—3 回合的账号仍是玩家数据，不能为了让统计“干净”而自动删除；
- 运营漏斗按“注册、创建命卷、首回合、3 回合、10 回合、次日、7 日”分别观察；
- 当前命卷使用四个可复用槽位；玩家删除后记录进入逻辑删除状态，不再展示或占用槽位，但短期保留内部审计与故障恢复依据；
- 结局与死亡属于故事事实，不复用“封存档案”作为玩家可见状态；旧版本测试数据只保留在内部历史层；
- 长期未活跃账号可以转为冷数据或不进入默认查询，但恢复登录后仍能找到命卷；
- 玩家主动注销时，应先结束会话、删除自备密钥，再按公开的数据规则删除或匿名化账号与命卷；
- 匿名统计不能保存邮箱、密钥、完整 Prompt 和剧情正文，也不能反向识别玩家；
- 正式扩大开放前，H5 需要提供用户协议、隐私说明、AI 生成内容说明、自备模型说明、注销与反馈入口。

具体保留期限和注销冷静期需要结合法律、备份恢复能力和实际运营流程另行确认，未确认前不得写死自动清理任务。

## 10. 新功能准入

任何新功能进入开发前必须回答：

1. 它保护哪一条产品承诺；
2. 属于哪个业务领域，谁是权威数据源；
3. 玩家、Agent、Java 和 H5 分别负责什么；
4. 会改变哪些事实，是否需要玩家确认；
5. 是否真的需要新表或新字段；
6. 如何兼容现有命卷并失败回滚；
7. 管理台如何观察但不干预剧情；
8. 如何用真实玩家回放、真实 RDS、真实模型和手机 H5 验证。

上述问题未确认前，不开始业务实现。
